# Проектная разведка тестового проекта — универсальный сборщик

## Назначение

Скилл анализирует **любой** тестовый проект (фреймворк-агностично) и собирает
**«проектную разведку»** — структурированный Markdown-отчёт с фактами и конвенциями,
которые затем использует другой агент для генерации корректных автотестов.

Скилл **не выдумывает** данные: каждый факт берётся из реальных файлов проекта, отсутствующие
паттерны помечаются как «Не обнаружено». Никакой привязки к конкретному продукту, бренду или
инфраструктуре — все выводы строятся на автообнаружении.

## Принципы работы (обязательные правила)

1. **Только факты из кода** — каждый пример сопровождается путём к файлу.
2. **«Не обнаружено»** — если паттерн не найден, пишем так, не подставляя шаблонные примеры.
3. **Не изменять исходный код проекта** — скилл только создаёт новый файл отчёта.
4. **Язык отчёта** — русский (если проект русскоязычный).
5. **Без привязок к продукту** — не искать и не требовать конкретных путей вроде
   `src/utils/route`, `allure-test-ops`, `markupTestOps`, конкретных тегов или правил из
   какого-то одного проекта. Всё определяется по факту наличия файлов.
6. **Формат** — `## <раздел>` → `### <подраздел>`, markdown-таблицы, код-блоки с языком.

## Общий план работы

При запуске скилл делает следующее:

1. **Запрашивает путь к проекту** (или берёт текущий каталог / `pwd`). Если путь указан —
   проверить, что он существует.
2. **Определяет тестовый фреймворк** по `package.json` и конфиг-файлам (см.
   `references/framework-detection.md`).
3. **Собирает метаинформацию** — `package.json`, конфиги фреймворка, `tsconfig.json`,
   линт-конфиги.
4. **Обнаруживает структуру проекта** — где живут тесты, утилиты, страницы/Page Objects,
   фикстуры, setup/auth.
5. **Читает репрезентативные тестовые файлы** — выборка **5–8 модулей из разных доменов**
   (папок), предпочтение самым крупным по размеру.
6. **Собирает конвенции и стиль** — по разделам отчёта (см. `references/report-template.md`).
7. **Генерирует Markdown-отчёт** `<имя-проекта>-project-intelligence.md` (путь по умолчанию —
   каталог проекта, можно уточнить у пользователя).
8. **Сообщает результат** — путь к файлу и список заполненных разделов.

## Автоопределение фреймворка

Приоритет: **наличие конфиг-файла** → **пакет в `package.json`**. Порядок определения:

1. Playwright  — `playwright.config.*` или dep `@playwright/test`/`playwright`
2. Cypress     — `cypress.config.*` или dep `cypress`
3. Jest        — `jest.config.*` / секция `jest` в package.json, или dep `jest`
4. Vitest      — `vitest.config.*`, или dep `vitest`

Сводная таблица по фреймворкам (конфиги, тест-глобы, раскладка, ключевые настройки) —
в `references/framework-detection.md`.

- Если совпало несколько фреймворков — берём **основной** (первый по порядку), остальные
  помечаем «Также присутствуют: …».
- Если ничего не совпало — пишем «Фреймворк не определён», делаем «слепую пробу»:
  смотрим тест-скрипты в `package.json` и топ-уровневые тест-каталоги.
- Монорепо/Nx: ищем конфиги лениво (из корня и из обнаруженных тест-каталогов), не
  предполагая один единственный конфиг.

## Структура отчёта

Отчёт — это `*-project-intelligence.md` со следующими разделами (полный шаблон и правила
оформления — в `references/report-template.md`):

1. Мета и версии
2. Тестовый фреймворк и конфиги
3. Структура проекта
4. Запуск и скрипты
5. Правила именования
6. Стиль кода и линт
7. Локаторы / селекторы
8. Page Object Model (POM)
9. Фикстуры (Fixtures)
10. Ассерты (Assertions)
11. Таймауты и ожидания
12. Тестовые данные
13. Хуки (Hooks)
14. Setup и аутентификация
15. Теги и маркировка
16. CI/CD
17. Артефакты и отчёты
18. Эталонный тест
19. Полезные выводы для генератора автотестов

Каждый раздел наполняется фактами из найденных файлов. Если раздел нечем заполнить —
«Не обнаружено».

## Как собирать разделы

Конкретные grep-команды и ключи настроек по каждому разделу — в
`references/generic-collection.md`. Общий подход:

- Конфиги — `Read` найденных конфиг-файлов.
- Структура — `ListDirectory`/`Glob` по тест-каталогам и утилитам.
- Локаторы/ассерты/хуки/теги — `Grep` по репрезентативной выборке тестов с подсчётом.
- Эталонный тест — `Read` 1–2 самых крупных тестов из разных доменов.

Числа «count» приводятся по выборке (из разных доменов), а не как точная глобальная
статистика — это оговаривается в отчёте.

## Формат вывода результата

```bash
✅ Файл <имя-проекта>-project-intelligence.md создан
Путь: <абсолютный путь>
Фреймворк: <Playwright / Cypress / Jest / Vitest / не определён>
Заполненных разделов: <N> / 19
```

Если часть разделов пустая — перечислить, какие именно «Не обнаружено».

## Прогрессивное раскрытие

Читать при необходимости:

- `references/framework-detection.md` — матрицы детекции фреймворков, конфиги, тест-глобы.
- `references/report-template.md` — шаблон отчёта и правила оформления разделов.
- `references/generic-collection.md` — техника сбора фактов по каждому разделу и grep-команды.
