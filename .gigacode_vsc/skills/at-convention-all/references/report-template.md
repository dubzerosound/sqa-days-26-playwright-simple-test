# Шаблон Markdown-отчёта «проектная разведка»

Файл отчёта: `<имя-проекта>-project-intelligence.md` (имя проекта — из `package.json` `name`,
или из имени корневой папки, если `name` отсутствует).

Цель отчёта — структурированный контекст для последующего агента генерации автотестов:
перечислены разделы, каждый наполняется **реальными фактами** из кода с указанием пути.
Если паттерн отсутствует — пишем **«Не обнаружено»** и **не подставляем** шаблонные примеры.

Язык отчёта: **русский** (если проект русскоязычный). Отступы: `## <раздел>` → `### <подраздел>`,
markdown-таблицы, код-блоки с явным языком (`typescript`, `json`, `bash`).

> Разделы не обязаны быть все — если проект маленький/минимальный, можно объединить
> смежные или отметить «Не обнаружено». Главное — не выдумывать.

---

## Обязательные разделы отчёта

### 1. Мета и версии

Факты:
- `name`, `description`, `version` из `package.json`
- движок Node/npm, если указан (`engines`)
- **определённый фреймворк** и его версия (из `package.json` или lock-файлов)

Формат:
```markdown
| Параметр | Значение |
|---|---|
| Название | <name> |
| Версия | <version> |
| Фреймворк | <Playwright / Cypress / Jest / Vitest / не определён> |
| Версия фреймворка | <из package.json> |
```

### 2. Тестовый фреймворк и конфиги

- Найденные конфиг-файлы фреймворка и их путь
- Ключевые настройки (для Playwright: `baseURL`, `timeout`, `retries`, `use`, `projects`,
  `dependencies`, `reporter`, `outputDir`, `expect`; для Cypress: `baseUrl`, `retries`,
  `video`, `screenshotOnRunFailure`; для Jest/Vitest: `testMatch`, `testEnvironment`,
  `setupFilesAfterEnv`/`setupFiles`, `transform`)
- Код-блок с ключевой частью конфига (цитата)

### 3. Структура проекта

- Где живут тесты (каталоги): `src/tests`, `tests`, `e2e`, `cypress/e2e`, `__tests__` и т.п.
- Где живут утилиты/хелперы, страницы/Page Objects, фикстуры, setup/auth, support
- ASCII-дерево с пояснением каждой папки

### 4. Запуск и скрипты

- `scripts` из `package.json` (полностью, в таблице)
- Команды запуска в зависимости от фреймворка (`npx playwright test`, `npx cypress run`,
  `npm test`, `npx vitest run`, ...)
- Как фильтровать по имени/тегу (если видно в скриптах или конфиге)
- CI-команды, если явно прописаны

### 5. Правила именования

- Паттерны тест-файлов: `.spec.ts`, `.test.ts`, `.cy.ts`, `-e2e.ts` (какие реально встречаются)
- setup-файлов
- утилит/хелперов
- классов (PascalCase), функций
- стиль именования тестов и `describe`-блоков (первое слово/«должен/проверяет/...»),
  теги — всё как зафиксировано в коде (факт, без жёстких требований)

### 6. Стиль кода и линт

- `eslint` / `tsconfig` ключевые настройки (`strict`, `extends`, правила)
- порядок импортов, если он систематичен (например, фреймворк всегда первым)
- запреты/разрешённые паттерны из конфигов и кода (наблюдаемые, как факт)

### 7. Локаторы / селекторы

- Приоритеты использования: `getByRole`, `getByText`, `getByTestId`/`data-testid`,
  `locator(CSS)`, `locator(XPath)`, `getByLabel`, `getByPlaceholder`
- **Фактический count** по каждому типу в выборке тестов
- `[data-testid]` — встречается ли, в каком виде

Формат:
```markdown
| Тип локатора | Использований в выборке |
|---|---|
| getByRole | N |
| ... | ... |
```
Пример из кода (1–2 цитаты с путём).

### 8. Page Object Model (POM)

- Есть ли классы с суффиксом `Page` / слово `PageObject`
- Или используются атомарные функции/хелперы
- Или «POM не используется» — тогда это фиксируем как факт (без навязывания шаблона)

### 9. Фикстуры (Fixtures)

- `test.use(...)` — как используется (Playwright)
- `base.extend(...)` / кастомные фикстуры — есть ли (Playwright)
- Встроенные фикстуры, которые реально применяются: `page`, `context`, `browser`, `request`, `testInfo`
- Cypress: кастомные `Cypress.Commands.add(...)` (аналог фикстур)
- Что именно это даёт для последующей генерации (компактный вывод)

### 10. Ассерты (Assertions)

- Наиболее частые матчеры: `toBeVisible`, `toHaveText`, `toContainText`, `toEqual`,
  `toHaveURL`, `toHaveCount`, `toHaveValue`, `should(...)` и т.п. — с относительной частотой
- Мягкие проверки: `expect.soft` (Playwright) / `soft(...)` (Cypress) — есть ли
- Наличие сообщений у ассертов (второй аргумент `expect(actual, message)`) — фиксируется
  **как факт** (как часто встречается, в каком стиле), но **не** как обязательное правило
- В API-тестах: `expect(...).toEqual`, статус-коды

### 11. Таймауты и ожидания

- `waitForResponse(...)` / `waitForRequest(...)` — с каким паттерном/url
- `waitForSelector(...)` / `waitForLoadState(...)`
- `waitForTimeout(...)` — встречается ли (отметить как возможный анти-паттерн, но фактом)
- `expect` timeout, `DEFAULT_*` константы таймаутов, `BACKEND_DELAY` и т.п.
- Кастомные функции ожидания в утилитах

### 12. Тестовые данные

- Константы/файлы данных (домен-специфичные и общие)
- `@faker-js/faker` / `faker` — импортируется ли
- Фабрики и генераторы (`generateString()`, `createUser()` и т.п.)
- Моки API / подмены ответов, если есть

### 13. Хуки (Hooks)

- `beforeEach` / `beforeAll` / `afterEach` / `afterAll` — частота использования
  (сколько тестовых файлов используют)
- `test.use({ storageState })` — в каких файлах, какие роли
- Cypress: `beforeEach` в `support`, `Cypress.session`
- Что исполняется перед каждым тестом (обобщённо)

### 14. Setup и аутентификация

- Setup-файлы (`.setup.ts`) и что они делают
- `.auth`/`storageState` файлы — какие сессии/роли
- Переменные окружения, управляющие setup (`SKIP_SETUP`, `CI`, базовые URL)
- Как происходит логин (не секреты, только механизм)

### 15. Теги и маркировка

- `test.describe(..., { tag: [...] })`, `test(..., { tag: [...] })` (Playwright)
- `describe.only`, `test.only`, `.skip`, `.fdescribe`, `.fit` — встречается ли
- Cypress: `testTags` (cypress-grep), репортеры; Jest/Vitest: `describe`, `test.concurrent`
- Все используемые теги списком (уникальные)

### 16. CI/CD

- Найденные CI-конфиги в репозитории (`.github/workflows/*`, `.gitlab-ci.yml`, `.circleci`, ...)
- Как запускаются тесты в CI, какие переменные окружения
- Если CI-конфигов нет — «Не обнаружено»

### 17. Артефакты и отчёты

- `reporter` (Playwright), allure, junit, html
- `screenshot`, `video`, `trace` настройки (Playwright)
- `outputDir`, `output/` и т.п.
- Cypress: `video`, `screenshotOnRunFailure`, `reporter`
- Jest/Vitest: репортеры, coverage

### 18. Эталонный тест

- 1–2 самых больших тестовых файла из **разных доменов** (по размеру), читать целиком/порциями
- Перечислить: импорты, `test.use`, хуки, `allure.step`/шаги, паттерн настройки→действие→проверка,
  тип ожиданий
- Привести ключевые цитаты кода с указанием пути и (желательно) номера строки

### 19. Полезные выводы для генератора автотестов

Компактный итог — правила, которые должен соблюдать агент генерации:
- какой фреймворк и какие команды запуска
- какие локаторы предпочтительны (из фактов раздела 7)
- какие ассерты/матчеры типичны (раздел 10)
- какой паттерн структуры теста (раздел 18)
- каких анти-паттернов избегать (например, `waitForTimeout`, если присутствует)
- чего не хватает / что улучшить (короткий бэклог, если очевидно)

## Правила оформления

1. Каждый пример кода — цитата из реального файла с указанием пути.
2. Пустой/недостижимый раздел → «Не обнаружено».
3. Никаких домыслов и шаблонных вставок, не подтверждённых кодом.
4. Таблицы — markdown, отступы 2 пробела, код-блоки с языком.
